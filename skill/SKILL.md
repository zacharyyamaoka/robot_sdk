# robot-sdk: assemble, don't rewrite

The goal of robot-sdk is that **building something new is mostly assembling sub-assemblies that already exist and already work.**
Each package is a stable, tested black box with a typed API.
An agent's first move on a robotics task is to find the packages that already solve it, not to write a script.

*Zach, 2026-11-23: "Our goal is to build up these tools as stable sub assemblies so doing anything new you are basically just assembling the things you have already done in the past!"*

## How to use this index

1. **Match the task to packages** with the table below. Most tasks touch two to four of them.
2. **Read the README of each matching package before writing code.** The README has the API, the quick start and the rules of that package. Then read its `docs/` (a `CONTRACT.md` or `docs/peps/` where one exists) and its `tests/`, which show real calls.
3. **Assemble.** Import the packages and pass the objects between them. They all join on `robot_msgs` types (`JointTrajectory`, `JointState`, `Pose`, `JointLimits`, …), so one package's output is usually another's input.
4. **When a piece is missing, add it to the package where it belongs**, following that package's README and the layer rule below. Don't write a one-off copy in your task folder. A gap you fill becomes the next sub-assembly.
5. **Say what you reused.** In your handoff, list which packages and functions you assembled and what you had to add.

**Where the code is.** Each package is its own git repo, named as in the table, at `github.com/zacharyyamaoka/<repo>`.
On a development machine the repos are checked out next to this one: if this skill is at `<root>/robot_sdk/skill/`, a package is at `<root>/<repo>/`. On Zach's machine `<root>` is `/home/bam`.
`pip install robot-sdk` installs the whole set at versions pinned to work together.

| **robot_msgs** | Py | The standard robot data types (ROS's geometry, sensor, trajectory and vision messages) as frozen Python dataclasses, *with* the functions between them: pose offsets, trajectory interpolation and resampling, point projection, depth to point cloud. `.show()` (Rerun) and `.plot()` (matplotlib) on every type. ROS 2 / bag export as an extra. Strict semver: additive changes only. | Any pose, transform, joint state, trajectory, limit, image or point cloud. **Never define your own Pose or Trajectory.** |
| **robot_models** (PyPI `robot-models-lib`) | Py | Generic physical models of part *types* (servos, arms, conveyors, end effectors, sensors), each a ladder of models from ideal to learned (M0 ideal → M1 datasheet → M2 Coulomb + viscous → M3 friction …). Every rung states its parameters, equation and references. No maker, no SKU. Imports robot_msgs and numpy only. | What parameters a model of an actuator or arm needs, which friction or dynamics model to use, how parameter names map. |
| **robot_controllers** | Py, C++ · partial | Controllers as black boxes: a robot_msgs message in, a `ServoCommand` out, `controller.tick(state, dt)`. Joint trajectory controller (Python and C++), joint impedance. Each benchmarked on a ladder of rungs (free motion, fast motion, impacts, pushes, replanning, host stalls) for performance and cost. | Tracking a trajectory, impedance or compliance, choosing a controller, host vs board control. |
| **robot_reach** | Py | Reachability of any arm in Cartesian and joint space, from FK and IK passed in as pure functions. Reach maps, joint maps, IK branches, orientations; save results, view them in viser, and hand them downstream as a `ReachableWorkspace` (`robot_reach.workspace`, from `ReachResult.workspace()`) whose named regions (reachable, top-down, hemisphere, dexterous, your own) sample IK-checked poses. Ready and rest poses: `robot_reach.rest` measures a pose's footprint, clearance and holding power over a scene, and `robot_reach.goals.solve` picks the best one for a use case (a `PoseGoal`: clearances, held or limp, readiness to a workspace, energy), whose record `to_named_pose` turns into a robot_msgs NamedPose. Example arms built in (pendulum, RR, five-bar, 3-DOF shoulder, UR5e); loads URDFs. | Workspace, "can the arm reach X", IK branch choice, sampling reachable poses for a task, placing a robot or a bin, arm sizing, choosing a ready or rest pose (and its NamedPose). |
| **robot_collision** | Py | Computes the Allowed Collision Matrix (SRDF disable_collisions) for one robot, several robots, or a robot and its scene: a robot description, or your own pure FK function plus bodies, in; a robot_msgs AllowedCollisionMatrix out, proved equal to brute force. Closed linkages (five-bar, delta) work through the description's own expand(q). Viewed in viser with a floating matrix window. | Which link pairs to collision-check, generating an SRDF, viewing a robot's collision pairs. |
| **robot_thermal** | Py | Running servo motors above their continuous rating in short bursts, safely. v1: an I²t burst budget per drive plus a hard cut on board temperature. v2: a lumped thermal network per drive, fed by logged current, with a Kalman observer. Standard library at runtime. | Motor or board heat, burst limits, duty cycles, how hard a joint may be pushed. |
| **robot_trajectories** | Py | A signal library for robot motion. Every trajectory kind is a `TrajectoryGenerator`: a plain function `f(JointSpace, numbers/points/poses) → JointTrajectory`, inside the limits and at rest at both ends. ~80 kinds: moves, waypoints (joint and Cartesian), random waypoints, pick and place, chirps, multisines, PRBS, step trains, PID tuning, friction ID, ISO 9283 tests, workspace sweeps, moving targets. `chain` / `split` to compose. The legs inside a kind are timed by a `WaypointTrajectoryGenerator` (points + joint limits in, a JointTrajectory out: minimum_jerk, trapezoid, ruckig, ruckig_pro, toppra as plugins), passed as `waypoint_generator=`. The robot (limits, FK/IK, dynamics, collision) is injected via `JointSpace`. | Generating any motion: test trajectories, excitation for system ID, pick-and-place paths, tuning signals, benchmarks. |
| **robot_autonomy** | Py | A library that counts working hours between human interventions, from every source (chat asks, logs, faults, tickets), and ranks their causes as a to-do list. Its loop (`AutonomyAgent.tick`) is plain code with no model in it: it ingests every source, scores the KPI and verifies each fix by measuring its cause go down. | Measuring and driving down human interventions; autonomy KPIs. |
| **robot_metrics** | Py | Performance metrics for robot parts: tracking error, stop error, lag, repeatability, with units. Works on a whole recording or a live feed, with identical numbers. Runs group into rungs, stations and deployments; pass/fail targets (objectives) are kept apart from the maths. Shaped like torchmetrics. | Scoring any run: target vs real, sim vs real, before vs after, pass/fail gates. |
| **robot_activity** | Py | A library that measures whether each robot is doing useful work (claimed, active, moving), keeps a work queue moving, flags stalemates and gives every idle second a reason. Its loop (`ActivityAgent.tick`) is plain code with no model in it: it prompts the owners of the work and never decides what the work is. | Fleet or robot utilisation, uptime dashboards, work queues. |
| **like_keras** | Py, C++ · partial | The communication API: components with ports, systems that wire them from outside, deployments in one process or across the network, over two backends (`inproc` threads and dora-rs 0.5). A component can also be C++, written against one header (`cpp/include/like_keras/lk.hpp`) and built with CMake's `lk_component()` into a `.so` that runs as a dora node or as a GIL-free real-time thread inside a Python process (`like_keras.native`). The frozen v0 contract is `docs/CONTRACT.md`. | Connecting robot components, sensors and processes; dataflows; a C++ real-time controller that swaps in for a Python one in one line. |
| **traj_compare** | Py | Viewers on robot_msgs types, in three parts. Comparison: a turn-key A/B trajectory viewer that writes one static `report.html` (target vs sim vs real). Trajectory coverage (`traj_compare.coverage`: how much of a robot's joint limits, workspace and tool orientations a set of trajectories visits) and grasp coverage (`traj_compare.grasp_coverage`: how much of a gripper's jaw range, approach directions, rolls and offered area a set of GraspPose uses, and where the failures sat), each one payload feeding a data-ui workbench, Matplotlib, Viser and W&B; grasp coverage is also deployed as its own grasp dataset viewer (`grasp_viewer` link). Coverage of any list of dataclass records moved to its own package, dataclass_coverage. | Comparing runs (target vs sim vs real, before vs after), benchmark reports, "how much of the space does this trajectory or grasp dataset cover?". **Never write a bespoke trajectory plot or coverage page.** |
| **robot_msg_viz** | Py | One curated Rerun view per robot_msgs type (blueprint, sample data, screenshot) on top of robot_msgs' own logger: `viz.show(msg)`, `viz.save(path, msg)`, `with viz.stream("arm") as live: live.log(msg)`, `viz.blueprint(...)` for your own recording. The landing page lists every type (supported ones clickable) and every use-case dashboard plugins add, each with Open in browser / Open on desktop. | Looking at any robot_msgs message in Rerun, live or from a file. **Never hand-write a Rerun layout for a standard type; grow its view here.** |
| **sim2real** | Py | The outer API on top of everything: digital twins (`RobotTwin`), one-click `.calibrate()` (configure → fit → tune → measure routines), MuJoCo simulation, and dashboards of how close each twin is to its real hardware. Stdlib-only core; the stock maths (numpy, robot_metrics, sim2real) is the `stock` extra, imported lazily. The io-diagnostics app (dashboard, device tree) uses it. | Is this robot, joint or sensor healthy? Pass/fail checks on runs, health dashboards, turning a metric into an alarm. |

### Close neighbours (not in the pinned SDK yet)

Look for these as sibling checkouts too. They are part of the same toolkit but are not on PyPI.
- **robotparts**: the parts catalogue (datasheets, SKUs, real arms such as the UR series). Its parts point at robot_models types.
- **bam_robot_descriptions** (inside `bam_ws/src/core/`): composable robot descriptions (parts composed into a robot, CAD-simplified and full-fidelity tiers).
- **pidtuna**: turns a robot description into tuned PD gains, analytic first, then measured on the robot.
- **dataclass_values**: `Value` / `Space`, the units-carrying values robot_msgs uses.
- **dataclass_coverage**: any list of dataclass records in (robot_msgs messages, JSON rows), how well it covers its declared space out; was `traj_compare.record_coverage`. Domain-free (numpy + dataclass_values, never imports robot_msgs), so it sits beside dataclass_values, not in the viewers layer.

## The layer rule

```
robot_msgs → robot_models → (robot_parts → robot_descriptions)
   → robot_trajectories · robot_reach · robot_controllers · robot_thermal · robot_metrics
     · robot_activity · robot_autonomy · like_keras
   → traj_compare (viewers: end points, nothing imports them)
   → sim2real
   → robot_diagnostics (checks over metrics and twins)
```

- A package imports only from layers below it. **Leaves never import each other.** When one leaf needs another's behaviour, it takes a function or a Protocol as an argument, and the caller passes it in. Example: `robot_trajectories` never imports a kinematics library; you inject FK/IK into its `JointSpace`.
- **Viewers are end points.** traj_compare may import robot_msgs and leaves; no package imports a viewer.
- **The type is the API.** Packages agree on robot_msgs types, not on each other.
- `robot_sdk/tools/check_layers.py` enforces the rule. Run `uv run pytest` in `robot_sdk` after you add a dependency anywhere.

## Example assemblies

These show the shape; check each package's README for exact names.
- **Trajectories for a new arm (e.g. a UR5e):** the arm's description → robot_trajectories `JointSpace.from_description(...)` (or `.from_limits(JointLimits)` plus injected FK/IK) → kinds such as `random_waypoints` / `joint_waypoints` with `waypoint_generator=` a Ruckig `WaypointTrajectoryGenerator` → robot_reach to confirm the targets are reachable → robot_metrics to score tracking.
- **Tune and verify a joint:** robot_trajectories `pid_tuning` / `step_train` → pidtuna for the gains → robot_controllers to run them → robot_metrics for tracking and stop error → robot_thermal to keep the bursts safe.
- **A twin of a rig:** robot_models for the rung and its parameters → sim2real `RobotTwin` and `.calibrate()` → robot_metrics and traj_compare to show sim vs real.

## Keeping this index true

The packages table is generated: each row is that package's own `robot-sdk.toml` (`summary` = what it is, `use_when` = reach for it when, `[links]`), so when a package gains a capability worth knowing about, update its `robot-sdk.toml` in the same change, then in `robot_sdk` run `uv run python -m tools.sdk_graph` and `uv run python -m tools.sdk_graph readme`. Never edit the table by hand; `uv run pytest` fails when it is out of date.
New package checklist: a `robot-sdk.toml` in the package's repo (`uv run python -m tools.sdk_graph draft <package>` prints a first one); a landing page declared as its `[links] site` (200 with real HTML, not a placeholder or a GitHub README) and linked from the package's README, or its health is never green (`uv run python -m tools.sdk_graph check --online` checks it); in `robot_sdk`, a pin in `pyproject.toml`, a `[tool.uv.sources]` line and a `LAYERS` entry in `src/robot_sdk/__init__.py`. Lay the package out as [`docs/package-layout.md`](../docs/package-layout.md) says: the core never imports like_keras; blocks go in `src/<pkg>/lk/` behind an `[lk]` extra.
