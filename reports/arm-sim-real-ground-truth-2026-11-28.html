The "HardwareInterface" you want already exists. It's Arm(deployment, backend="sim") in robot_msgs. Sim → real is the one word backend=. For ground truth, keep the typed state.truth that's already there. Give it a gym-style info slot only once a second kind of truth needs one: object poses for grasp success are next.
  • Your description/table/connect split is what the code has. ArmDeployment is your "configured, calibrated description" (joint table plus one factory per backend), and Arm(...) is the live handle. I'd add no third name.
  • When the arm is already running, you don't build a second Arm. One process opens the USB. Everything else attaches to it through like_keras with a write lease, the pattern from this morning's pendulum run. The remote handle isn't fragile if it's only a pipe: the joint table and limits are applied once, in the process that owns the bus.
  • The missing piece is an "attached" backend, so a script reads the same whether the arm is in-process or remote. It's sketched below and not built.

1 · Bring-up script, no middleware, one-word switch ran today

This is the UR5e bring-up path that landed in the JCC box (bringup/run.py), cut down to the loop. The sequence file is static data.

# bringup/sequences/02_move_elbow.py — one step per line
SEQUENCE = JointCommandSequence(name="move the elbow", steps=[
    hold(PAN, CAP[PAN]),
    hold(LIFT, CAP[LIFT], GRAVITY[LIFT]),
    move_by(ELBOW, +0.3, max_vel=0.5, max_effort=CAP[ELBOW], feedforward_effort=GRAVITY[ELBOW]),
    move_by(ELBOW, -0.3, max_vel=0.5, max_effort=CAP[ELBOW], feedforward_effort=GRAVITY[ELBOW]),
])

# the runner
arm = Arm(UR5E, backend="sim")            # backend="real" on the rig: the only line that changes
controller = JointCommandController(arm.joint_names)
controller.submit(SEQUENCE)
state = arm.read()
while controller.status == "executing":
    tick = controller.tick(state, arm.period_s)
    arm.write(tick.command, tick.defines)
    state = arm.read()

state.truth          # GroundTruth on sim, None on real (the Arm strips it on real)

What made the ROS remote arm fragile, and the rule that avoids it: the proxy kept its own copy of things: model, limits, offsets, cached state. Then the two drifted. Ground truth: 5 proposals

The question: on real you get command and measured. On sim (or with an oracle) you also want the truth, without forking the loop.

Criteria (weight)

  • Same loop on sim and real (5). Switching the backend changes no other line.
  • Can't leak onto real (5). A test that asserts on truth can't pass on hardware by accident.
  • Open-ended (4). Room for object poses, contacts, grasp success, not just joints.
  • Typed and logged with the sample (4). Same stamp, recorded, comparable later.
  • Usable online (3). A gate can check it inside the loop.
  • Lightweight (2). Little new API.

P1 · Gym-style info dict

state, info = arm.read()          # info = {} on real; {"truth": ..., "contacts": ..., "objects": ...} on sim
info.get("truth")

It's clean and you can dump anything in it. But it's untyped: keys drift between backends, a typo reads as "no truth", and every read() call site changes shape.

P2 · Typed state.truth landed c72d664

state = arm.read()
state.truth                       # GroundTruth(name, position, velocity, effort, stop_effort, source) | None
state.truth.of("elbow_joint")

One loop. Truth rides on the same sample with the same stamp, and the Arm strips it on real (pinned by test). Its limit is joint truth only.

P3 · Separate truth channel

state = arm.read()
truth = arm.truth()               # raises / absent on real; an lk Out port only the sim component has

ServoState stays untouched, like Gazebo's /model_states topic. But you align two streams by stamp, and on real the call or the port isn't there, so the wiring differs.

P4 · The oracle is a sensor in the cell

cell.oracle.state()               # sim: MuJoCo; real: ArUco bundle / OBSBOT / mocap — same component, same type

This is the only option where an oracle test can also run on hardware: approximate truth from a real sensor. That fits your 11-11 rule (encoders gate, ArUco secondary). Truth is only as good as the sensor, and it's heavier to build.

P5 · Truth only in the recording

arm = Arm(UR5E, backend="sim", record="run.mcap")   # sim writes the whole world: every body, contact, joint
# tests and traj_compare join it to the run by stamp afterwards; read() carries nothing

No API surface at all, and it holds everything the sim knows. But you can't gate on it inside the loop.

Pick: P2, with P1's openness inside it, plus P5 for the rest

  • Keep state.truth as the one place truth lives. What's good about gym's info is "one bag for everything the sim knows". GroundTruth already is that bag; it just only holds joints today.
  • When the first non-joint truth is needed, give GroundTruth a typed objects field (body name → pose), or an info mapping if it really is grab-bag. That's grasp-success detection, so it's the next one. It's typed where you test on it and free-form only where you only look at it. Not built until then.
  • Use P5 for everything you only look at afterwards (contacts, all bodies). The sim already records to mcap/rrd.
  • P4 is the long road to truth on hardware, and it's already partly there in camera calibration. It should be a separate component, not part of the Arm.

Part 2 · HardwareInterface from a description (later the same day)

Renamed: Arm → HardwareInterface (robot_msgs 292b832). Pick for the API: a deployment record holds typed backend configs (P4 + P2). Its ad-hoc form is HardwareInterface.from_robot_description(rd, MujocoConfig(gui=False)), mirroring your own RobotTwin.from_robot_description(rd) from Nov 17.
  • "MuJoCo no friction" vs "MuJoCo realistic" isn't two backends. It's one backend fed two sets of description parameters: nominal values with friction 0, vs the sim2real fitted twin's .parameters. That answers your last question. Configuring how the robot shows up is configuring the description. The backend config only says how the run happens: GUI, realtime factor, timestep, seed.
  • There are two kinds of backend, and that decides what "each part implements its own backends" means. Real drivers and per-actuator models are per part, so the cell composes them. MuJoCo and kinematic are whole-scene: they compile the whole subtree into one model. Both show up as the same HardwareInterface.
  • Remote isn't a sixth kind of robot model. It's a transport. Its config is an address plus the description fingerprint it expects. The far end is any other HardwareInterface, which could itself be 1–5. Local, LAN and cloud differ only in the address scheme.

  • Nov 12/16, the layers: robot_msgs → robot_models → robot_parts → robot_descriptions, with sim2real on top. The HardwareInterface type and backend protocol sit in robot_msgs. Backends sit with the parts and simulators that implement them. Composition happens at the top.

Remote: confirming it's the same robot

hw = HardwareInterface(BAM_FB_PILOT, "core")
# handshake: the client sends fingerprint(description + parameters + joint names); the core compares it with its own
# mismatch → RemoteMismatch("core serves bam_fb_pilot@3f0a…, you expect bam_fb_pilot@9c41…: description differs in link_3 mass")

The fingerprint covers what the robot is and its joint names, not its CAN ids. A client never sees the CAN ids, and a rewired core is still the same robot to a script. The attached-backend agent is adding the handshake now.

"From CAD to the real robot, completely autogenerated": almost

Three things are still not in the CAD. Each has a way to stop being hand-typed:

  • Which board drives which joint (the JointTable). Discover it: scan the bus, then wiggle each board a few degrees and see which joint's encoder or the camera moves. That's generated, not typed.
  • The homed zero. That's calibration, not generation: hw.home() writes it into the table.
  • The real parameters (friction, masses). That's sim2real's calibrate(), which writes the fitted values next to the description.

So the honest phrase is generated → discovered → calibrated. All three are automatic, and only the first comes from CAD.
