Your note, sharpened: yes, put one thin Arm between the controllers and the bus. And there's a sharper reason than "it's tidy". A bought arm (a UR5e, an xArm, everything in robotparts.arm) already is this box: you send it joint names and positions and never see a servo. Our arms are the only ones where CAN ids leak upward (the JCC track's cases name joints can11, and bam_fivebar/reachable.py:43 hard-codes {"j2": {"can_id": 12}, "c1": {"can_id": 13}}). The Arm makes our servo arms look like a bought arm.

What the Arm does, exactly, so it stays light. It does the 1:1 per-servo things from the transmission rule, and nothing else:

  • name ↔ servo address (bus, CAN id): the thing you want gone from commands
  • sign, offset and the homed zero: your "what if you want to apply a joint offset or a zero?" case. The homed map is runtime state, which the Arm reads after homing.
  • which transport (fdcanusb, pi3hat, twin): your "if I change from CAN USB I shouldn't need to change my code"
  • Not the five-bar. The Arm's joints are the servo joints (j2, c1), and the coupling stays in the robot model (decision B above).

P1 · Arm is a role, its binding is a joint table (config, not code)

class Arm(lk.Component):                        # role: ports only, joint-named
    command = lk.In(ServoCommand, lagged=True)  # name = ("j1", "j2", "c1", "w1", ...)
    state   = lk.Out(ServoState)

# rig config (TOML or a frozen dataclass), the only place a CAN id lives
JOINTS = JointTable(bus="fdcanusb:/dev/serial/by-id/…", joints={
    "j2": Servo(can_id=12, sign=-1, offset_rad=0.30),
    "c1": Servo(can_id=13, sign=+1, offset_rad=0.00), ...})

dep = lk.Deployment(cell, bind={Arm: ServoArm(JOINTS, homed="~/.local/state/…/latest.json")})   # REAL
dep = lk.Deployment(cell, bind={Arm: TwinArm(JOINTS, plant=...)})                                # SIM

✅ the thinnest box that does all four jobs · ✅ the table is data, so renumbering is a config edit · ➖ a bought arm binds at the role too, but a UR5e wants trajectories, not 500 Hz ServoCommands

P2 · Two layers: Arm (names) over ServoBus (ids)

bus = ServoBus(transport=Fdcanusb("…"))         # speaks ids: bus.send({12: cmd, 13: cmd}); bus.read() -> {12: state, ...}
arm = Arm(bus, JointMap(j2=Servo(12, sign=-1, offset=0.30), c1=Servo(13)))
arm.send(ServoCommand(name=("j2", "c1"), position=(...)))
bus.send({12: ServoCommand.stop()})              # bring-up: one servo, by id

✅ the debug path is a real, named box · ➖ two boxes where your note wants one · ➖ ServoBus is exactly what the moteus library already is

P3 · The Arm is a robot part: robotparts.connect()

arm = robotparts.connect("bam_fb_v2", transport="fdcanusb", homed=latest_homed())   # our arm
arm = robotparts.connect("universal_robots_ur5e", host="192.168.1.20")              # a bought one, same Arm
arm.send(command); state = arm.read()           # joint names from the part's datasheet

✅ criterion c is perfect: one call for every arm in the catalog · ✅ the joint table lives with the part's datasheet · ➖ puts live drivers into the catalog repo (robotparts is datasheets today) · ➖ CAN ids are per rig, not per part, so they still need a config beside it

P4 · The Arm owns the controllers (an Arm = a UR-style cabinet)

with lk.System("bam_fb_v2") as arm:              # the Arm IS manager + JTC + JCC + joint table + bus
    ...
    arm.expose(trajectory=jtc.trajectory, goal=jcc.goal, state=io.state, result=jcc.result, stop=mux.stop)
planner(state=arm.state); arm(trajectory=planner.trajectory)     # callers never see a ServoCommand

✅ matches how bought arms work (the UR cabinet runs its own JTC) · ✅ "robot abstracted" at the highest level · ➖ it's a System, not a thin box: callers can't reach the servo-level Arm without opening it

P5 · No Arm box: rename at the wire

bus = MoteusBus(transport=..., names={"j2": 12, "c1": 13})   # the driver translates names to ids

✅ least code · ❌ no home for sign, offset or the homed zero, so they'd leak back into the rig runners (today's ServoMap problem) · ❌ every transport re-implements naming

Scores are 1-3 per criterion, multiplied by its weight. They're my judgement, made explicit so you can disagree with one cell.

Pick (my default, easy to switch): P1, with P4 falling out for free. The servo-level Arm role is the thin box, bound by a joint table. The System that wraps Arm + manager + JTC + JCC is what a planner talks to. like_keras's pick_cell already calls it arm_controller(). A UR5e binds at that System level (its cabinet is the JTC). Our servo arms bind at the role level. Both have the same outside: trajectory, goal, state, result, stop. P2's debug path is kept as a method on the REAL binding (ServoArm.servo(12)), not as a box.

Prior art: ros2_control's <ros2_control type="system"> hardware component, which lists joints and puts per-joint params (CAN id, sign) in the robot description, is P1. Viam's arm component (joint positions in, no motors visible) next to its motor components is the P1 + P4 split.

What it takes:

  1. a frozen JointTable / Servo(can_id, sign, offset_rad) dataclass
  2. ServoArm(table, homed), built from today's bam_fivebar/plant.py ServoMap and boards.py can_id
  3. TwinArm from the rack twin
  4. rename the JCC track's can11 joints to names
  5. one test: renumber a CAN id in the table and nothing else changes
